# Wave C — Advisory (Advise)

## C0. Orientation
**Advise = governable candidate *response*.** It generates **Recommendations** and **Clarification Requests** — *things to consider*, anchored to the Findings/Issues that motivate them. Advise **does not** evaluate, govern, accept, or execute. Resolution Paths are **presentation-only** (AMB-1, Wave E): multiple Recommendations, no object.

## C1. Implementation Contract — IC-WC-ADVISE
- **Owner:** Advise (single). **Objects:** Recommendation (types: Suggested Action, Candidate Improvement), Clarification Request. **Reads:** Findings (Infer), Issues + assessment (Evaluate), Attested knowledge. **Produces:** Recommendations, Clarifications (Derived). **Consumed by:** Disclose (Wave E), User Acceptance (Wave U).
- **Required behavior:** (1) generate **Recommendations anchored to a Finding/Issue** (never standalone) — advisory only; (2) generate **Clarification Requests** when ambiguity blocks understanding (an *information request*, not an action); (3) emit `Recommendation Generated` / `Clarification Requested` and **append a Cognition History Record** per emission (via 00R); (4) on recompute, **re-derive and supersede** (live replaced, history appended); (5) support **multiple Recommendations** as alternatives (no Resolution-Path object).
- **Forbidden:** evaluate severity/confidence (Evaluate's); write canonical/promote to Attested; **govern exposure or authorize/execute** (Authority inactive; execution is Future); **accept** its own recommendation (acceptance is the user's); change assessment outside recompute.
- **Invariants:** advisory-only · anchored to Finding/Issue · Derived/non-canonical · only-recompute-changes-assessment · emission appends history · alternatives persist as multiple Recommendations · never authorizes/executes.

## C2. QA Contract — QA-WC-ADVISE
- **Positive:** Recommendation generated + anchored to its Finding/Issue; Clarification raised on blocking ambiguity; emission appends a Cognition History Record; recompute supersedes prior (records intact); multiple alternatives coexist.
- **Negative (impossible/rejected):** standalone Recommendation (no anchor); a Resolution-Path **object** created; Advise evaluating/scoring; Advise governing/authorizing/executing; Advise **accepting** its own output; a Recommendation changing without recompute; history overwrite.
- **Failure classification:** Critical — Advise governs/authorizes/executes or self-accepts; writes canonical; history overwrite. Major — unanchored recommendation; missing history append; Resolution-Path-as-object. Minor — metadata gaps.

## C3. Observability — OBS-WC-ADVISE
- **Events:** Recommendation Generated; Clarification Requested; Cognition History Record appended; (downstream) accept/reject/defer captured by Wave U. **Audit:** anchor lineage (which Finding/Issue), model/rule version. **Replay:** record-exact per emission; derivation **semantic** (many valid phrasings). **Drift/Trust:** unanchored/standalone recommendation, history overwrite = trust failures; Recommendation drift across history = product feature.

# Wave U — User Acceptance & Reconciliation (non-governance)

## U0. Orientation
**The user is the acceptance authority; OSLO records and reasons.** When a user **confirms** a planning item — accept a Recommendation, **edit/author directly**, or otherwise commit — OSLO (1) **captures** the action (Perceive), (2) **records** a **User Acceptance Record** *and* the **user-attested plan fact** (Retain, append-only, canonical), and (3) later **reasons** over it via the **Acceptance-Impact Assessment** (Infer/Evaluate, Derived). **No Authority engine.** Per Plan-Fact Clarification (§0.1): the confirmed content becomes **factual in the plan** (user-attested), **not** an OSLO world-truth claim.

## U1. Implementation Contract — IC-WU-ACCEPT
- **Owners (no new responsibility):** **Perceive** (capture) · **Retain** (record, append-only) · **Infer/Evaluate** (reconcile) · **Disclose** (surface). **Objects:** **User Acceptance Record** (user-attested Attested), **user-attested plan fact** (Canonical Fact attributed to user), **Acceptance-Impact Assessment** (Derived).
- **Required behavior:**
  1. **Capture** the confirmation action (accept / reject / defer / direct-edit) with the **specific item + version** referenced (Perceive).
  2. **Record two canonical items** (Retain, append-only): **(a)** the **User Acceptance Record** ("U confirmed I at T"), **version-pinned** to the accepted item's **Cognition History Record** (for Derived items) or attestation id; **(b)** the **user-attested plan fact** — the confirmed content as a **Canonical Fact attributed to the user**. OSLO's original Recommendation **stays Derived** in history.
  3. **Reconcile on drift** (Infer/Evaluate): when evidence/confidence/feasibility/alignment/outcome-confidence change vs. the version-pinned acceptance beyond tolerance (Calibration Defaults §3: ≥10 pts or band change), emit an **Acceptance-Impact Assessment** ("a decision you confirmed is affected") — Derived, appends a Cognition History Record.
  4. **Surface** acceptance state + impact alerts (Disclose, Wave E).
- **Forbidden (the seven (G) invariants):** user acceptance does **not** make content **world-true**, **not** OSLO-accepted, **not** active Authority; a User Acceptance Record **is not a Governance Decision**; acceptance is **append-only** history; the impact comparison is **Derived Cognition**; any OSLO-level acceptance/approval/override/execution stays **Future**. Also: never overwrite an acceptance/plan-fact record; never auto-promote OSLO's Derived recommendation (the **user** authors the plan fact).
- **Invariants:** plan-fact (user-attested) ≠ world-truth · acceptance ≠ governance · version-pinned · append-only · one-way flow preserved (user authors; OSLO doesn't promote).

## U2. QA Contract — QA-WU-ACCEPT
- **Positive:** a confirmation captures the item+version; **both** a User Acceptance Record **and** a user-attested plan fact are written (append-only); a direct edit writes a plan fact (with intake provenance) even without a recommendation; drift beyond tolerance raises an Acceptance-Impact Assessment; reject/defer recorded without creating a plan fact.
- **Negative (impossible/rejected):** acceptance marking content **world-true / OSLO-approved**; a User Acceptance Record treated as a Governance Decision; acceptance/plan-fact record **overwritten**; an acceptance **not version-pinned**; OSLO **promoting its own** recommendation to Attested (vs. the user authoring it); the impact comparison treated as canonical rather than Derived.
- **Failure classification:** Critical — acceptance-as-world-truth / as-governance; record overwrite; OSLO self-promotion. Major — missing plan fact on confirm; missing version-pin; impact not raised on drift. Minor — metadata gaps.

## U3. Observability — OBS-WU-ACCEPT
- **Events:** User Confirmation Captured; User Acceptance Record appended; Plan-Fact recorded; Acceptance-Impact Assessment emitted. **Audit:** who/when/what-confirmed/version-pin; the **acceptance→emission** linkage; the plan-fact's user attribution. **Replay:** **record-exact** for acceptance + plan-fact (Attested); **derivation semantic** for the Acceptance-Impact Assessment. **Drift/Trust:** acceptance-as-truth, record overwrite, missing version-pin = trust failures; **Acceptance-Impact (decision drift)** = product feature surfaced to the user.
