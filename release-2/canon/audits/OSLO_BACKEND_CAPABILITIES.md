# OSLO — backend capabilities the prototype SIMULATES (capture for the R2 build)

_Living list. The official R2 prototype (`oslo-prototype-r2.html`) fakes these in-browser (in-memory state, setTimeouts, demo controls). Each is a REAL backend capability the R2 build must provide — do not treat the prototype's stub as the spec for behavior, only for UX intent. Last updated: 2026-08-08._

## ⚖️ STANDING RULE — prototype simulation ⇒ backend obligation (owner, 2026-08-08)
**Any capability the prototype simulates or demonstrates MUST be designed and built by the backend to actually support it.** A demonstrated behavior is a product commitment, not a shortcut: a stub proves UX *intent* only — it is never the spec for behavior and never a substitute for a real implementation. **No prototype-demonstrated capability ships to users without a backing real build** (design + implementation + tests + the doctrine boundaries each entry names). This document is the running registry of that obligation: every entry below is *owed*, and every new simulated/demonstrated prototype capability must be added here the moment it appears — the list is not optional bookkeeping, it is the backend backlog.

## 1. Re-analysis engine (the "analysis update") — BATCH / event-driven
- **Prototype stub (OLD):** acting on an issue flipped it to "Addressed · updating…", then a fixed `setTimeout(1500ms)` marked it "Resolved" per item. This wrongly implied a synchronous per-fix re-read.
- **CANON (verified 2026-08-01, oslo-knowledge-base):** re-analysis is **event-driven and BATCHED, not per-fix.** Plan-affecting actions (confirm/flag/apply-fix/answer/route-response/edit) do NOT each trigger a re-read; they enqueue change-events. A reanalysis pass runs on **debounce windows + event consolidation + analysis queues + cooldown + incremental reanalysis** (I20-E1; I8/AE-03 "event-driven recompute … idempotency, debounce, no-change→no-reanalysis"), with an explicit **"Trigger Reanalysis"** affordance also allowed (60-Sec Orientation; Editing Workflow §H). Between a change and the next pass, the assessment is **STALE = "based on previous analysis,"** explicitly labelled (a "Pending Analysis" state) — content changed, assessment has NOT. **Reanalysis is the ONLY operation that changes assessment** (CAF/Reliability/Confidence/Findings/Recommendations/integrity/pillar bands). Reanalysis is **suggested** (advisory, keep working) vs **required** (before relying on the read as current) — thresholds deferred (§S). On completion, findings **weaken / stay unchanged / are superseded / close** (append-only supersession; prior retained in history). This IS the honesty backbone: "only the analysis resolves an issue, never a manual step" — now literally true because a manual call only enqueues; the batch re-read resolves.
- **R2 must provide:** the above engine — idempotent, auditable, fast per pass (~1–2s perceived), with the debounce/consolidation/cooldown queue and the stale-state contract.
- **Prototype simulation (target):** a call → item goes "Stale · pending reanalysis" (recorded, Undo-able, does NOT move the read); a debounce/cooldown timer (or explicit "Reanalyze now") fires ONE consolidated batch re-read (single countdown dial) that resolves the batch together and steps integrity once. See ai-first-candidate close-step / batch-model notes + `mock_batch.png`.

## 2. Provenance / attestation ledger
- **Prototype stub:** in-memory item state (`inf`/`addressed`/`you`/`fixed`/`routed`), `basisNote`, `attestedBy`, `HISTORY[]` array.
- **R2 must provide:** a durable, append-only **attestation record** per load-bearing detail — who confirmed/flagged/attested/mitigated, on what **basis** (documented / vendor-or-owner verified / verified directly / answered), timestamp, and whether it's the user's own evidence vs. attributed to another person. Provenance classes ("From OSLO" vs "Confirmed by you" vs "Confirmed by {name}") must be first-class and immutable/auditable. **Withdraw** (reversibility) must roll the ledger back with the reversal recorded, never silently.

## 3. Reviewer round-trip ("Ask for evidence" / routing)
- **Prototype stub:** "Ask for evidence" sets state `routed`; a "Simulate reply (demo)" button calls `respondRoute()` to fake approve/reject. Contacts (`PM_CONTACT`, `EXT_CONTACT`) are hardcoded.
- **R2 must provide:** real **request → notification → async response** flow: identity for the reviewer (collaborator vs scoped external), a delivery channel (email/in-app), a **scoped review surface** (external gets only the one question + its source; collaborator sees the full read), the reviewer's response captured as **attributed evidence** that grounds the read (or a rejection), and pending-state tracking until they answer. Includes the **k-factor invite** ("invite them to their own read"). Governs access — the external reviewer must NOT see the whole plan.

## 4. Evidence-vs-comment (discussion)
- **Prototype stub:** `commentOnIssue()` pushes to a local `COMMENTS[]` array; project-level only.
- **R2 must provide:** real **comment threads with @mentions and notifications**, scoped per-issue and per-project, kept strictly **separate from evidence** — a comment is discussion and must **never** ground the read or resolve an issue (doctrine D133/CR-2). The system must enforce that only an evidence-attestation (not a comment) changes the read.

## 5. Clarification loop
- **Prototype stub:** each item has a hardcoded question (`CLARIFY[key]`); the user's typed answer is stored (`clarifyAnswer`) and grounds the item locally with a canned basis note. No real understanding of the answer.
- **R2 must provide:** OSLO **generating** the right clarifying question for a given gap (real NLU/model call), **interpreting** the free-text answer, **updating the underlying project info/plan** from it (the answer may change a value, not just confirm it), and triggering re-analysis so the issue closes on the new state — not a hardcoded Q&A. The answer becomes attributed evidence in the ledger (cap. #2).

## 6. Plan-change application (Apply this fix / Write my own / Select an option)
- **Prototype stub:** `_applyPlanChange()` mutates in-memory arrays (adds a statement to an artifact, flips an EXWBS task); `_undoPlanChange()` reverses it. Content is authored by hand.
- **R2 must provide:** OSLO **drafting a concrete plan edit** for a given issue (model-generated, plan-aware), applying it to the real plan artifacts with **versioning + reversible history**, and re-analysis to reflect it. "Write my own fix" must deep-link to the right artifact/statement in a real editor. The honesty rule must hold: applying a fix firms **Viability** (the plan changed) but does **not** fabricate **Grounding** (the figure is still unverified) — the backend must keep those two dimensions distinct.

## 7. Band / integrity computation
- **Prototype stub:** `viaLevel()`/`grdLevel()`/`adaLevel()` are simple counts (grounded count, artifact-weakness fraction + a bounded mitigation credit, checkpoint count). Bands are a 4-level enum.
- **R2 must provide:** the real **Outcome-Integrity model** — weakest-gates min(Viability, Grounding, Adaptability), each computed from actual plan analysis (CAF-style clarity/alignment/feasibility for Viability, grounded/inferred ratio for Grounding, outcome-checkpoint coverage for Adaptability). Must be maturity-not-forecast (never a probability of success) and move only on real change.

## 8. Outcome checkpoints (Adaptability)
- **Prototype stub:** `CHK_PROPOSALS[]` hardcoded; adding one flips a counter and draws a marker on the timeline lens.
- **R2 must provide:** OSLO **proposing real, plan-specific checkpoints** (dated gates tied to workstreams, with the re-read rule and the proposed course-correction), writing them into the actual schedule, and evaluating them as execution progresses (drift detection).

## 9. Sharing / snapshots
- **Prototype stub:** the Share door describes a "revocable snapshot"; no real sharing.
- **R2 must provide:** real **revocable, access-scoped read snapshots / links**, with audit of who viewed what, and revocation.

## 10. Reports / narrative projection + roll-up dashboard
- **Prototype stub:** `_narrativeProjection()` string-builds a readout from in-memory state; export buttons are stubbed toasts. The **◱ Roll-up** owner door (`rollupDoorHTML`) likewise derives a live summary (integrity+gate+trend, calls awaiting the owner, who's-grounding-what, progress bar) purely from in-memory state; every row deep-links into the read (no server aggregation).
- **R2 must provide:** real **generated readouts** (recipient-tailored, summary/full), framed as a projection of the committed read (not a new assessment), and real export (PDF/PM-tool handoff — Asana/MS Project/Smartsheet). The roll-up is the same primitive as a **live owner dashboard**: server-side aggregation of the integrity model (#7), attestation ledger (#2), and reviewer/routing state (#3) into an at-a-glance owner view — read-only (it must route into the read to act, never act itself), and role-scoped (owner vs delegate-PM vs external). No new backend beyond #2/#3/#7 feeding it.

## 11. Multi-project + persistence
- **Prototype stub:** single hardcoded project (DevNorth 2026); "Projects" door is a mock; state is in-memory and resets on reload.
- **R2 must provide:** **persistent** per-project state, a real projects home/list, and load/save.

## 12. Identity, roles & access
- **Prototype stub:** `roleType` var ('owner'/'pm'/'other') toggled in code; no auth.
- **R2 must provide:** real **auth, identities, roles (owner / delegate-PM / scoped external), and access control** governing what each role sees and can attest. External reviewers must be scoped to a single question.

## 13. Notifications / awareness
- **Prototype stub:** the bell/Awareness door reads a local `HISTORY[]`; a numeric badge.
- **R2 must provide:** real **notifications/awareness feed** — routed-item responses, comments/@mentions, analysis updates, drift alerts — across channels.

## 14. Ask OSLO (chat) → governed-agent layer  _(P2, deferred)_
- **Prototype stub:** `sendChat`→`_osloExec` regex intent parser drives the same governed functions as the buttons; `window._EXP` instrumentation.
- **R2 must provide (when P2 is greenlit):** real **NLU** (not regex), ambiguity/confirmation turns, and governed action execution with the same attestation/provenance guarantees as the buttons. See `ai-first-candidate-research-backlog.md` (governed-agent layer, deferred until Tier 1 defined).

## 15. Funnel instrumentation / analytics
- **Prototype stub (UPDATED 2026-08-04):** activation/engagement are now derived in-page from `confirmCount` + `freezeOn()` (`_isActivated()` = confirmCount≥1 per DL-173; `_isEngaged()` = past unlock + ≥1 further act); the freemium intent moments log to `_INTENT_LOG` (#16), and the survey trigger carries an internal `_SURVEY_TRIGGER_AB` A/B knob (#18). All still in-memory, reset on reload — no persistence, no server events.
- **R2 must provide:** real **activation/funnel event telemetry** so activation, engagement, and experiments are measured, not inferred — including a durable event stream for the intent signals (#16), feedback/ticket events (#17), and survey responses + trigger-variant assignment (#18) so the readiness gate and the timing A/B become real signal, not modeled.

## 16. Freemium tiering, cardinality & intent-capture  _(R2 freemium scope)_
- **Prototype stub:** the unit of value is the **outcome** (DL-172); Free = 1 active outcome : 1 plan, kept narrow. Cardinality, archive/reactivate (`_outcomeArchived`, `vmArchiveSwitch`/`reactivateOutcome` — non-destructive, record kept) and the three **intent moments** are faked in-memory: **VM-1a** (add a 2nd outcome), **VM-1b** (start a 2nd plan), **VM-2** (intake envelope — too many/too-large files). Each is a NON-GATING mirror that names the paid capability, records intent to `_INTENT_LOG` (`{vm,tier,ctx,ts}`; tier kept internal), and offers the real free path (archive-to-switch) alongside the intent path (keep-both). User-facing copy is **NEUTRAL** — no paid-tier name/price anywhere.
- **R2 must provide:** real **plan/tier model + entitlement checks** (outcome as the metered object; container=plan; Free=1 active), **non-destructive archive/reactivate** with the record never metered, and a durable **intent-signal event stream** (which wall fired, when, chosen path) feeding #15 — so Alpha's "capture intent, don't upgrade" strategy produces real demand data. Nothing here gates the record, the reviewer/CRR loop, or Viewers. Neutral copy is a product rule, not a stub artifact — keep tier names/prices out of user-facing surfaces until the owner rules otherwise.

## 17. In-app product feedback (ticketing)  _(R2 freemium scope)_
- **Prototype stub:** the "✎ Feedback & rating" door files feedback to an in-memory `_FEEDBACK_LOG`. Each item is a lightweight **ticket**: auto id (`DEF-####`/`ENH-####`/`NOTE-####`, per-type sequence via `_fbNextId`), category (defect/enhancement/other), title, text, `status:'Filed'`, ts. A **defect** additionally carries structured `expected` + `impact` (blocking/slowing/minor) + auto-attached `context` (`_fbContext()`: current view · role · grounded X/Y · first-run flag). A "Filed this session" list echoes the tickets. Nothing is transmitted; feedback is explicitly held separate from the read (never grounds/changes it, never written to History).
- **R2 must provide:** a real **feedback/ticket intake** — durable storage, delivery to the team's tracker (or an internal queue), the defect **reproduction context** captured for real (view/route + sanitized state, **never** plan content), de-dup/triage fields, and status lifecycle beyond "Filed." Must preserve the doctrine boundary: feedback is a side channel — it must be structurally incapable of altering a user's read, band, issues, or History.

## 18. Readiness survey (PMF + experience) & its trigger  _(R2 freemium scope)_
- **Prototype stub:** the same door hosts the survey → in-memory `_SURVEY_LOG`: the **Sean Ellis PMF** question (very/somewhat/not disappointed), a 1–5 experience rating, and open text. It is **triggered, not just pull**: `_surveyNudgeHTML()` renders a fire-once, dismissible nudge in the read only when `_surveyTriggerEligible()` (activated + engaged, not yet answered/dismissed/opened). An internal `_SURVEY_TRIGGER_AB` knob ('immediate' vs 'delayed') is staged for a later live timing A/B. Single-session only — the nudge simulates a would-be next-session prompt.
- **R2 must provide:** durable **survey storage + response analytics** (PMF distribution → the ~40%-"very disappointed" readiness gate; CSAT trend), a real **audience-targeting/trigger engine** (post-activation + engaged, cross-session cadence, fire-once-per-user with cooldown, honoring dismissal), and **experiment assignment** for the timing A/B — all feeding #15. The survey must remain a readiness signal with no effect on the user's read (same boundary as #17).

## 19. Trade-off / tension detection (primary-dragging weaknesses)  _(Tier-1 honesty floor)_
- **Prototype stub (added 2026-08-08):** the DevNorth sample **hard-codes ONE trade-off as authored content** — an inferred Scope "edge" item (`s3`) + a static `ISSUES` entry (`sponsor-tradeoff`, Viability, `t:{artifact:'scope'}`) + guard `noSoundWhileUnsurfacedPrimaryTradeoff`. It is **not detected** — it is scripted, framed in single-outcome terms, and gates integrity (via Scope weakness) until the owner grounds it. It demonstrates the UX/doctrine; it does not find anything.
- **R2 must provide:** real **detection of genuine trade-offs/tensions in a plan that drag the PRIMARY outcome** — plan-aware analysis (model + rules) that finds where work, assumptions, or scope compete with the primary (resource / attention / budget / scope tension), surfaces each as a **load-bearing issue in primary-outcome terms**, gates integrity until the owner resolves it (draws the line / adjusts / accepts on the record), and re-reads on resolution. Feeds #7 (integrity), #1 (reanalysis), #2 (attestation ledger); resolvable, no dead-end.
- **Doctrine boundary:** this is the **Tier-1 honesty floor** — freemium gates capacity, never judgment quality (DR-7), so surfacing a real weakness in the primary must be **FREE**, even when the tension's root is a secondary outcome OSLO read but the user hasn't adopted (framed single-outcome, **no 2nd outcome modeled**). Detecting/naming a conflict **between two ADOPTED outcomes** (multi-outcome) is the separate **Tier-2** capability (cross-outcome conflict, `T2-MO-7`) — explicitly NOT this. Requirement spec: `release-2/OSLO_R2_TIER1_HONESTY_FLOOR_REQUIREMENT_DRAFT.md`.
- **⚠️ FUTURE WORK — "Draw the line" resolution is still simplified (owner note 2026-08-08).** The prototype now lets the owner *author* the boundary (OSLO drafts one static line via `_TO_LINE_DRAFT`; owner edits free text → written into Scope, grounds it). More is needed for the real build: (a) OSLO **generating a plan-specific, context-aware boundary proposal** (not one hardcoded string) from the actual budget/agenda/scope; (b) **structured** boundary modeling (what's in vs. out, per sponsor-activation dimension) rather than a single free-text blob; (c) **re-analysis on save** — drawing a tighter/looser line should ripple to dependent artifacts (budget, agenda, attendance) and may open/close other issues, not just flip this one to grounded; (d) **validation** that the drawn boundary actually resolves the tension vs. merely declaring it resolved; (e) attribution/provenance of the boundary decision in the ledger (#2). Treat current draw-the-line as UX-intent only.

## 20. Accepted-exposure register + re-raise  _(honesty: accepted ≠ resolved)_
- **Prototype stub (added 2026-08-08):** the trade-off card resolves inline via two decisions — **Draw the line** (`_drawTheLine()` → grounds the Scope boundary, `prov:'you'`) and **Accept on the record** (`_acceptExposure()` → new `prov:'accepted'` state). Accepting leaves the gate (`artWeak` only gates on `'inferred'`) but the item persists in a first-class **Accepted exposures** tray (`_acceptedTray()`, amber/owned, never green) and as a distinct **Accepted · owned** bucket in the issue-layer door — reversible via `_withdrawAccepted()` (re-opens + re-gates). All in-memory; the "re-raise on drift" is described in copy, not actually computed.
- **R2 backend must provide:** a durable **accepted-risk register** as a first-class object distinct from resolved and from mitigated-needs-grounding — each accepted exposure recorded in the attestation ledger (#2: who accepted, when, basis "accepted with eyes open"), **carried into readouts/reports (#10) and the owner roll-up**, and **re-surfaced by re-analysis (#1) and outcome-checkpoints (#8) when conditions drift** (an accepted risk is monitored, not forgotten). Reversible (withdraw rolls the ledger back and re-opens the gate). Doctrine: accepting is a mature decision that leaves the gate (no longer a *blind* gap), but it must **never** read as eliminated/safe — grounded ≠ safe, level ≠ trust. **Boundary:** this is single-outcome (a trade-off against the primary); it is NOT the Tier-2 cross-outcome machinery.

## 21. Progressive analysis stream + `analysis-complete` signal  _(onboarding arc / fast pass)_
- **Prototype stub (spec 2026-08-08, not yet built):** the onboarding arc (`ONBOARDING_ARC_STORYBOARD_SPEC_2026-08-08.md`) runs over the ~60s fast pass in two modes — Guided (narrated) and Watch-it-work (their plan analyzed live, findings surfacing). To show findings *forming*, and to hand off to the first decision exactly when analysis is done, the prototype will fake a **progressive event stream** and a **completion event** with `setTimeout`/scripted reveals.
- **R2 backend must provide:** the fast pass emits **progressive/streaming analysis events** during the pass (plan structure parsed → inferred nodes identified → pillar reads populating → findings/issues detected), plus a definitive **`analysis-complete`** signal the arc gates activation on (never on a timer). Most arc content is *existing-engine output the arc consumes* (outcome, plan tree, inferred nodes, pillar reads, the traceable load-bearing inference — capabilities #1/#7/#19) — only the **streaming delivery + completion event** are new here. Doctrine: the live view must show *real* forming state, never a fake progress theater; if a value isn't computed yet, don't render it as if it were.

## 22. Plan ingestion → typed, labeled plan-tree + node-level finding provenance  _(onboarding arc)_
- **Prototype stub (added 2026-08-08):** the onboarding arc reads the DevNorth sample and renders it as THEIR plan — a typed hierarchy (outcome → deliverables → workstreams → tasks → inferred assumptions) where each element is introduced by its TYPE and then its real label ("DELIVERABLE → Revenue & sponsorship", "ASSUMPTION → Wi‑Fi capacity is sufficient"), and each of the three judgments' findings is pinned to the specific element it derives from (Grounded "assumed — not verified" callout on the Wi‑Fi assumption node; Viable finding on the sponsor deliverable; Adaptable on the outcome). All hardcoded (`nameThePlan()`, `wifiNode`/`sponsorDel`, per-beat `tagNode`) — the labels and the finding→element links are authored, not extracted.
- **R2 backend must provide:** (a) **ingestion + structured extraction** of the user's real plan into a typed plan tree — classify each element (outcome / deliverable / workstream / task / assumption-or-inference) and carry a human-readable label from the source; degrade honestly on a thin brief (never fabricate elements or labels). (b) **Node-level finding provenance** — every finding/judgment (Viability / Grounding / Adaptability, #7/#19) references the specific plan element(s) it derives from, so the assessment is auditably "based on your data" and the UI can anchor each finding to its element. Feeds #7 (integrity), #2 (attestation/provenance), #21 (the arc/live view consumes this).
- **Doctrine boundary:** the read must be **derived from the user's actual plan** — no generic/canned findings presented as if plan-specific; if the brief is too thin to support a specific finding, say so rather than invent one (honesty-first; the arc's guardrail "never fabricate specifics"). Typing/labeling an element must reflect what's really in the plan, not impose a template.
- **Refinement (2026-08-09):** the arc now renders **assumptions and inferences as two distinct node types** (assumption = plain hollow amber ring; inference = hollow amber ring with a **dashed inner ring**, `itype:'inference'`) with distinct labels, and shows a **workstream as a labelled cluster** bracketing its child tasks while the **deliverable stays a single node**. Backend must therefore classify gap-fills into two provenance classes — **assumption** (the plan takes it on faith) vs **inference** (OSLO derived it to complete the plan) — each auditable, not merged into one 'inferred' bucket. Plan-specific terms in the narration are also marked (`.pd`) so personalizations are legible.

## 23. Non-persistent guidance prompts + durable engagement signal  _(onboarding / UX honesty)_
- **Prototype stub (added 2026-08-09):** guidance prompts must not persist to blindness, so several retire on demo-timed, SESSION-scoped logic: the readiness-survey nudge auto-retires after `SV_NUDGE_TTL` (45s, wall-clock) shown+ignored, re-offers after `SV_NUDGE_SNOOZE` (120s), caps at `SV_NUDGE_MAX` (3) then stops for the session (`_svNudge*`); the pillar-coach chip auto-retires after appearing on `COACH_MAX` (2) distinct cards (`_coachCards` set); the left-rail "Take a quick tour" chip hides once `_isEngaged()`. All gate on `_isEngaged()` (`confirmCount>=3`), a demo proxy for "value experienced" that RESETS ON RELOAD.
- **R2 backend must provide:** (a) a **durable, per-user engagement / "onboarded" signal** (real active-engagement metering, not a `confirmCount` proxy or a reload-reset flag) that prompt-retirement and coaching gate on; (b) **cross-session persistence** of each prompt's seen/shown/dismissed/retired state, so a returning engaged user never re-sees a first-run prompt and a snoozed prompt re-offers on the real cadence; (c) **owner-configurable cadence** for the survey (TTL / re-offer / max) and coaching (max exposures) as real config, not hard-coded demo constants (see `DEMO_VS_PRODUCTION_AUDIT_2026-08-09.md` G1). Feeds #15 (telemetry) and #11 (persistence). **RATIFIED 2026-08-09 (owner):** 'engaged' = a MILESTONE (>= half the load-bearing read grounded OR integrity up >=1 band; config default 1/2), NOT a click count; plus a durable per-user 'onboarded' flag (completed first-run once, ever). See DEMO_CONFIG_REGISTER.md.
- **Doctrine boundary:** no guidance prompt may persist until the user goes blind to it (owner 2026-08-09); retirement must be honest (hidden because the user is engaged, not silently expired mid-need). Demo timings are wall-clock and MUST be replaced by active-engagement metering — a demo value must never ship as the SLA/cadence.

## 24. Multi-format plan export (file) + PM-tool push  _(export / interoperability · tiered)_
- **Prototype (added 2026-08-09):** the export modal (`openExport` → `_exportModalHTML`) offers **Download a file** in four formats built from the executable plan (`exLeaves()` → task · owner · dates · provenance · note): **CSV** (`_planCSV`), **Excel** (`_planXLS`, HTML-table workbook), **Text** (`_planTXT`) and **PDF package**. CSV/Excel/Text are **REAL** client-side downloads (`_dlFile` → Blob + `<a download>`, filenames like `devnorth-2026-plan.csv`); PDF is still a simulated package. Separately, a Basic-gated **Push your plan to Asana** row (`_asanaSyncNow`, paywall `_PAYWALLS.asanaSync` tier `basic`, `_payGate('asanaSync')`) — on Free it's locked (🔒 Basic → commitment gate); on Basic it runs a simulated **one-way** push. Guard `exportMultiFormatGated`; `exportFlowReal` retained.
- **R2 backend must provide:** (a) **server-side generation** of each export format from the governed plan — a real **.xlsx** (not an HTML-table `.xls`), a real **PDF** package with the advisory disclaimer on the cover, plus CSV/Text — each carrying task · owner · dates · **provenance** (grounded/inferred/proposed) and dated to the analysis behind it (D153 disclaimer); (b) **PM-tool integration** to Asana (and others) via their APIs. **Tiering (owner 2026-08-09, aligns DL-206):** manual file export (download → import yourself) is **FREE**; a **ONE-WAY push/import** into the PM tool so the user can *view* the plan there is **BASIC** (updates stay manual in OSLO; re-push to reflect changes); **TWO-WAY sync + execution monitoring** is **PRO**. Never present Basic as "auto-sync"/bi-directional.
- **Doctrine boundary:** exporting runs **no new analysis** — it's a projection of the governed read, dated, with the advisory disclaimer (maturity, not a forecast). Freemium gates the **automation/capacity** (the push, the sync, the monitoring), never the judgment quality or the record — the file export and the accuracy bar stay free on every tier (DR-7). What crosses to the PM tool is the executable plan only; OSLO keeps the plan of record.
